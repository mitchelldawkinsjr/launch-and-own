# Acceptance for protected Cloudflare Pages PR previews

**Release gate** — Keep Git previews off for approved launches until the site owner and Domain approve a per-site access policy and an independent test confirms it. Use the existing session-protected, exact HTML or ZIP review for private pre-publication review. The three `esp-*` projects in the #83 read-only audit reported GitHub source, `main` production and `preview_deployment_setting: none`. Check each other project independently. [#83](https://github.com/mitchelldawkinsjr/launch-and-own/issues/83) · [#86](https://github.com/mitchelldawkinsjr/launch-and-own/issues/86) · [Safe website updates](./SAFE_WEBSITE_UPDATES.md)

Git-connected Pages offers `all`, `none` and `custom` for automatic previews. Custom evaluates excludes first, then includes, then skips unmatched branches. A leading or trailing `*` matches zero or more characters. The proposed per-site policy uses `custom`, the single include `launch-and-own/site-*`, an explicit `main` exclusion and `pr_comments_enabled: false`. Reconcile that exact comparison across both PRs. Confirm `main`, automatic production deployments and build/watch settings independently. A prefix match triggers a build on a push even before a PR exists. GitHub rulesets can restrict matching branch creation and updates, subject to plan availability and bypass actors. Private repositories need GitHub Pro, Team or Enterprise Cloud for repository rulesets. Verify who can write the preview namespace on the target repo and exercise allowed and unrelated writers and refs in the pilot. Leave previews off when those controls cannot enforce the reviewed workflow. [Pages branch controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/) · [Cloudflare API schema](https://github.com/cloudflare/api-schemas/blob/main/openapi.json) · [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)

Pages preview links are public by default. The project dashboard's **Settings → General → Enable access policy** creates protection for preview hosts under `*.<project>.pages.dev`. Access wildcards cover one hostname level. Confirm the effective allow policy and path coverage for both deployment hash hosts and mutable branch aliases. A more specific Access application can take precedence for a path. Production `<project>.pages.dev` and any custom domains are outside this preview policy. A preview alias can also be mapped to a custom domain. Verify every such route is protected or absent before enabling builds. A private GitHub repo, an obscure URL, `noindex`, a disclosure and an Access app covering a different host provide zero evidence that preview content is protected. [Pages previews](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Access application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/) · [Pages known issues](https://developers.cloudflare.com/pages/platform/known-issues/#enable-access-on-your-pagesdev-domain) · [Custom branch aliases](https://developers.cloudflare.com/pages/how-to/custom-branch-aliases/)

Pages Free currently publishes 500 builds per month and one concurrent build per account. Eligible pushes can consume build capacity before a PR link is available. Confirm the site's account plan, available capacity and operating cost before seeking consent. Surface queued, failed and skipped builds, quota exhaustion and retry timing from observed provider evidence. Keep any link withheld when the provider is unavailable or inconclusive. ## Implement and verify in order

1. **Detect under the verified owner.** Derive the immutable GitHub user/repo ID, Cloudflare account ID and Pages project ID server-side from active grants and #39 inventory. Check `GET /user`, private repo, matching owner, managed marker and `main`. Read the exact project in the selected account and match its ID, name, subdomain, GitHub source, owner and `repo_id`, production branch and approved static build settings. Compare `owner_id` when provided by Pages. A conflicting or missing required identity stops processing. A site that predates the feature takes the same read-only checks. Existing configs describe build behavior. Report `none` as disabled for new builds, surface other settings to the owner for review and reserve `active_verified` for current protection and deployment evidence. [#39](https://github.com/mitchelldawkinsjr/launch-and-own/issues/39) · [Pages project API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/methods/get/)
2. **Explain and approve the per-site policy.** Show the exact account, site, source, targeted changes, reviewed Access audiences and host scope, build usage, and disable and cleanup behavior. Bind the owner's separate browser approval to the account, project, repo, production/source checks, observed and desired settings, effective access and branch policy, action and expiry. Re-read and invalidate a changed target, expired approval, revoked grant or authorization epoch. An opt-in for a site's build policy and a later approval to publish the exact edit each need their own evidence. [#86](https://github.com/mitchelldawkinsjr/launch-and-own/issues/86)
3. **Prove protection before eligible pushes.** Qualify the plan first with synthetic content in a disposable project in an independently consenting account. Establish the Access policy before enabling eligible builds. Check that an allowed Access identity receives the intended content and that a fresh anonymous browser and a second, unapproved identity cannot receive it. Test a root page, direct asset and deeper path on the immutable URL, branch alias, retained deployment URL and any other host that can serve the preview. Exercise role removal and session expiry. Match the Access application and policy to the same Cloudflare account and preview hosts and check for bypass, broad allows and more specific conflicting applications. Establish the same protection on the intended site before allowing an eligible branch to build. Withdraw link eligibility when evidence expires or any policy or grant drifts. Check provider-native GitHub statuses, comments and deployments for links as part of the pilot. [Pages previews](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Cloudflare GitHub check runs](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/#check-runs)
4. **Apply and verify only in a separately authorized release.** A read-only plan can describe the exact intended diff. Hold the PATCH executor until owner, Domain and orchestration approval of the verified policy. Check that source identity, production deployments, build/watch settings and unrelated configuration survive. Establish how to prevent concurrent provider edits from overwriting or invalidating the reviewed change. Re-read on lost or ambiguous responses before considering a retry. Verify the exact resulting config, effective access, canonical production and owner grants. Leave the private in-app workflow available when configuration or access verification fails. [Pages update API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/methods/edit/) · [#2](https://github.com/mitchelldawkinsjr/launch-and-own/issues/2)
5. **Pin the approved update at PR creation.** Keep the private exact review and separate existing authorization to create a PR. Record the reviewed base SHA and HTML SHA-256, derived `launch-and-own/site-<20 hex>` ref, exact verified staged commit, and GitHub PR number in server-controlled approval state. For one-page updates, verify the SHA-pinned homepage and the approved diff at that commit. Check that GitHub returns the same head SHA and both repo IDs. On read, require an open same-repo PR targeting `main`, current base equal to the approved base, and exact ref and head SHA confirmed by both the PR and branch reads. Recheck authorization and freshness before exposing a result. A branch name or a new current head cannot establish approval. ZIP review and publication continue through their separate exact-bundle flow. [Update approval and status](../onboarding/site-update-flow.mjs) · [GitHub pull request API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)
6. **Verify the protected deployment before exposing its link.** Resolve the deployment from the verified Pages project. Require its immutable project and deployment IDs, `preview` environment, GitHub push trigger, exact ref and full head SHA, and successful, non-skipped `deploy` stage. Confirm Git source on the deployment when returned. Use the provider's immutable HTTPS URL with the deployment's `short_id` under the verified Pages subdomain. Reject branch aliases, custom or unrelated origins, credentials, extra path, query or fragment, and ambiguous URLs. Verify the exact homepage bytes at `/` through the approved Access session. Pages can redirect HTML filenames to their extensionless routes. Keep provider API credentials out of content requests. Release the link only within the authenticated owner surface with current protection proof. Suppress it from errors, logs, unauthenticated output and cached responses. [Pages deployment API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/methods/get/) · [Serving Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/)
7. **Require manual merge and independent production verification.** After the owner merges the reviewed GitHub PR, use GitHub's verified merged commit SHA. Check the matched, immutable Pages project and its canonical successful production deployment at that SHA, then check HTTPS `/` on the production hostname against the approved HTML SHA-256. A pending, stale or mismatched result stays pending or blocked. Keep update status reads free of deployment triggers. [Production verifier](../pipeline/verify-site.mjs) · [#30](https://github.com/mitchelldawkinsjr/launch-and-own/issues/30) · [GitHub pull request API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)

## Rollback and stop conditions

- **Stop future preview builds.** Suppress link display and stop issuing eligible updates if protection, grant or policy evidence lapses. With separate owner and Domain approval, restore `preview_deployment_setting: none` on the verified project and confirm the read-back. Keep its Access protection in force. Confirm an intended synthetic preview ref produces no new deployment and verify that canonical production and its HTML are intact. Published deployment hash URLs can remain available after automatic builds stop. Check retained hashes, aliases and mapped hosts anonymously and with a denied identity. Delete only individually approved preview deployments where supported. Cloudflare documents that the latest deployment for a branch cannot be deleted. Keep Access in place and escalate any still-reachable deployment. Pages retains 30 days of deployments plus exceptions for its 100 newest and current production. [Pages previews](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Pages retention](https://developers.cloudflare.com/pages/platform/limits/#deployments)
- **Revert published content through Git.** Record current `main`, canonical production commit and expected restore digest. Open an owner-reviewed revert PR against current `main`. Inspect the intended restored bytes and preserve unrelated intervening edits. An owner merges it manually. Verify GitHub's actual revert merge SHA on `main`, the successful canonical Pages production deployment of that SHA and the exact restored HTML bytes. Verify the next separately approved Git update through the same checks to establish source and production convergence. An emergency Pages rollback requires a separately authorized, still-retained successful production deployment. It changes serving state immediately, so reconcile `main` through the revert PR before resuming routine updates. [GitHub revert PR](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/reverting-a-pull-request) · [Pages rollbacks](https://developers.cloudflare.com/pages/configuration/rollbacks/)

Domain reported a separately owner-approved trial on one owner QA project. The read-back went `none` → `custom` → `none` and preserved the reported Git source and production settings. Production returned HTTP 200. The inactive include list ended as `[]` in place of its original `["*"]`. Protection enforcement, retained preview URLs and canonical production SHA and HTML still need evidence from the protected pilot. [Domain's trial report](https://github.com/mitchelldawkinsjr/launch-and-own/issues/86#issuecomment-7089724208)

A disposable Git rehearsal merged a synthetic change, reverted it on a reviewed branch, merged the revert, then merged a further synthetic update. The revert preserved an intervening asset change. Stubbed Pages responses produced `pending-expected-commit` for the old Pages rollback SHA with matching restored bytes, `pending-expected-html` for the correct Git revert SHA with stale bytes, then `live` for matching production SHA and bytes. The next change stayed pending until both matched again. All eight simulated requests were reads.

## Acceptance evidence to record

| Case | Expected result |
| --- | --- |
| Approved new launch and existing project | Synthetic creation sends `none` with automatic production on. Missing configuration, `all`, unsupported custom rules and retained URLs surface as review cases. Read-only inspection makes zero provider writes. |
| No protection or drift | Missing Access scopes/role, open policy, unrelated app, uncovered path, linked custom host, expired approval and revoked grants each withhold the link. Allowed and denied browsers confirm enforcement at the provider. No reliance on the application hiding URLs. |
| Source or revision mismatch | Replaced repo/project, wrong account, fork, wrong ref, stale base, moved head and closed PR all suppress links. A move during verification requires fresh review. |
| Deployment and usage | Skipped, queued, failed and wrong-project/branch/SHA builds, quota errors and tampered or redirecting provider URLs withhold links. Matching protected deployment and bytes open the approved immutable preview for the owner. |
| Publication and reversal | Preview success leaves release pending until manual merge and exact canonical production checks. Simulate stale canonical SHA, stale HTML, successful Git revert and another Git push. Live release requires the same sequence in the independent pilot. |

Record redacted permission and policy evidence, expected IDs and digests, state transitions, and screenshots that omit protected URLs, tokens and private content. Run `npm test`, `npm run qa:distribution` and `npm run preflight:onboarding`; include recovery checks when changing the Worker or durable flows. Track CI and independent one-page launch/edit acceptance in #21 and rollout approval in #2. This review uses public provider evidence and synthetic verification. Protected Pages rollout and the provider rollback drill remain gated on the separately consenting pilot.
