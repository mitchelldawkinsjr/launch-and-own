## Permissions and privacy decisions

- The public Launch & Own GitHub App manifest currently reports `contents:write`, `metadata:read`, `pull_requests:write` and `repository_creation:write`. Actual access is scoped to the user's app installation. Check the immutable user and repository IDs with current grants. Cloudflare's separate Workers & Pages app needs approved access to the intended repository. [App](https://github.com/apps/launch-and-own) · [Pages GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/)
- Onboarding requests Cloudflare OAuth `account-settings.read page.read page.write offline_access`. Page reads cover project metadata. Cloudflare's GraphQL account analytics requires Account Analytics Read for account-level data. The standalone RUM list uses Account Settings Read, and RUM writes require Account Settings Write. Neither a RUM site record nor a Pages analytics tag establishes that a beacon is currently deployed or that metric values were measured. Separate verified permissions and actual data are required for a metrics response. [Cloudflare API schema](https://github.com/cloudflare/api-schemas/blob/6468b0158971220db1a76ee20f7b64e1826f030e/openapi.json) · [GraphQL token authentication](https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/)
- Pages injects analytics JavaScript on the deployment after enablement. That can change served HTML while GitHub source bytes stay the same. Keep the dashboard action framed as reviewing the provider's settings. Activation requires the owner to approve the beacon and what it collects, and an acceptance test must preserve exact public HTML verification. A possible later design commits an explicitly reviewed beacon as approved content, after verifying how the provider registers the site. Continue reporting absent measurements as unavailable. [Enable Web Analytics](https://developers.cloudflare.com/pages/how-to/web-analytics/) · [Data collection](https://developers.cloudflare.com/web-analytics/data-metrics/data-origin-and-collection/)
- Pages preview deployments are public by default. Git status checks and branch aliases can disclose their URLs independently of the toolkit. Verify Access on the exact preview host pattern and every alias **before any eligible branch push**, with both a rejected unauthenticated request and a signed-in allowed viewer. Current app scopes contain no Access app/policy verification scope. Use the supported provider-managed setup and review path until protection and approved head are proved. Use an immutable hash-based deployment URL only after that proof. [Preview settings](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Branch controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/)
- A branch prefix limits builds and provides no evidence about who approved a commit. Future #86 integration needs a server-pinned PR head after verified exact artifact creation, immutable head and base repo IDs, exact approved base, current repo/project ownership, a ready preview deployment for that branch and SHA, and separately verified protection. Preserve the private Launch & Own review. Use a separately reviewed Git revert PR for normal rollback so GitHub source and canonical deployment can converge. [#86](https://github.com/mitchelldawkinsjr/launch-and-own/issues/86)

## Dashboard integration and later releases

### #87 with #39, #30 and #41

The projection's `viewer` is the authenticated, current provider-linked owner. `reference` comes from server-side owned-site resolution (#39) and contains the stable site ID, immutable GitHub user and repo IDs, Cloudflare account and Pages project IDs, repository name, branch and source kind. Provider observations are fetched with fresh grants and fenced against logout or account changes. The selected Cloudflare account must be the account used for the Pages API path. The projection returns `null` on mismatches. GitHub descriptions are editable, so matching the managed marker helps discovery and grants no write authority.

`publication` is optional server-side evidence with the approved commit, canonical deployment and project and repo identities, matching approved and observed public HTML digests, and the verification timestamp. `verified_deployment` means the current project metadata matches the deployment whose bytes were last verified at `verifiedAt`. A production deployment can be reported as observed while verification remains pending. A different canonical deploy ID or SHA removes the verified link and keeps the previous timestamped evidence as historical context. A dashboard GET can use existing evidence or a GET-only verifier of the same immutable project and exact bytes. The approved first-build path in `verifyWebsite(..., { approved })` can start a deployment and belongs to launch orchestration.

The current launch history is scoped to unexpired rows and lasts 30 days. A history-first display can say **Last verified at …** for a saved successful job. Treat an approval hash as approval evidence. An uploaded site's empty `approved_html` field provides no public HTML digest. Stable discovery, present-day provider status and latest-source editing belong to #39. Resolve owned sites while keeping private HTML, archives and OAuth grants under their respective retention policies. For the history view, project the required display fields from one owner-scoped read and keep private artifact columns out of that query. Render authorization failures separately from empty history. #41 owns shared visual and Worker route integration review. Test mobile and desktop presentation and no-store ownership checks before a hosted release. [Local QA runbook](BETA_QA_ACCEPTANCE.md)
