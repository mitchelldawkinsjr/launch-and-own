# Durable launch jobs

## Decision

Persist approvals and job progress in the dedicated Launch & Own D1. Deliver due work through the existing five-minute Worker Cron and a best-effort attempt after an approval response. D1 records the approval before either path can contact a provider. This lets a launch survive a dropped HTTP request, lost response, or Worker interruption. The runner can resume within the currently approved one-hour session. After expiry, disconnect, or loss of either provider grant, it waits for the verified customer to reconnect and explicitly approve the stored website again.

D1 plus Cron keeps one source of truth for approval, leases, recovery and retention and uses the existing DB and Cron bindings. The beta processes at most one job per tick and handles the first attempt through the Worker when possible. The five-minute cadence and account quotas constrain throughput. Verify D1 and Workers usage at the expected beta load, including CPU and subrequests. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

Queues would provide independent delivery and configurable retries, with a producer, consumer, delivery operations and an outbox or reconciliation step between D1 and the queue. Workflows would provide durable step execution and instance retry controls, with a new binding, separate execution history and limits on retained instances, steps and storage. Both would still need to consult the same D1 approval and active authorization fence before provider calls. Revisit either as latency or concurrency grows. [Queues delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) · [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/) · [Workflows pricing](https://developers.cloudflare.com/workflows/reference/pricing/)

## Approval and authorization

1. The preview freezes the normalized static HTML in the browser session. The review form includes a SHA-256 digest over the approval version, job ID, verified tenant identifiers, target, plan and exact HTML bytes. CSRF and exact-origin checks protect the form. A transactional D1 batch conditionally records the immutable snapshot, session authorization and private review state. A concurrent duplicate or stale form cannot attach authority or create another job for the same target.
2. A job has independent uniqueness for the GitHub user ID and repository slug and for the Cloudflare account ID and Pages slug. It records the approved plan, HTML, digest, initial approval and expiry timestamps, progress, retry data, lease and safe error code. It also records the GitHub repository ID, branch, commit SHA and, once provisioned, the Pages project ID. A separate short-lived link binds the job to the approving session and its authorization epoch. OAuth credentials stay AES-GCM encrypted in the session table.
3. Each attempt verifies the GitHub user ID and selected Cloudflare account through their APIs, refreshes grants with the existing provider-specific leases when needed, and rereads the primary D1 lease and session immediately before each outbound request. The read requires enough lease and session lifetime for the bounded call. The other provider's access is checked again before GitHub mutations or Pages creation. Credentialed requests reject redirects.
4. Disconnect atomically deletes the local session and cascades its launch bindings before attempting provider revocation. Replacing the browser's GitHub session, reconnecting Cloudflare, or changing the selected Cloudflare account invalidates the previous authority. An account switch away and back still increments the epoch. A provider rejection or failed refresh pauses the job. A competing refresh lease defers it within the retry budget. Multiple browser sessions carry their own approvals and provider authorization.
5. The history screen rechecks both providers before exposing an owner's launch rows. Resume freezes the original artifact in a new private review and requires approval again. It preserves the original job ID, checkpoints and expiry. The old lease must expire before another session can take over. Current live entries link to the verified site and can be removed from history.

### Threat model

| Threat | Control and remaining boundary |
| --- | --- |
| Another tenant requests a job, preview, or delete by ID | Session-scoped preview queries and job history scoped to immutable GitHub user ID plus Cloudflare account ID. State-changing requests require exact origin, CSRF and verified account access. |
| Changed content or replayed approval | Digest and compare-and-set against the stored preview, transactional approval, stable target uniqueness and one session binding. A runner rechecks the immutable snapshot before network access. |
| Two runners or a dropped provider response | Conditional claim with random lease ID, identity and authorization checks on each call, compare-and-set on progress writes, and deterministic provider names. Recovery reconciles identity, source and content before reuse. |
| Logout, provider revocation, or expiry during work | A session delete or epoch change fences later calls. A provider call already admitted can finish, and provider revocation can race with a request. The application cannot atomically combine a D1 read with a provider write. It checks authorization at the call boundary and keeps the lease fence during authorization loss. |
| Repository or project substituted out of band | Check the stable provider IDs, private visibility, exact job marker, branch, Git tree and pinned homepage bytes. Verify the Pages source and static build settings. Once recorded, the repo ID, branch, SHA and Pages project ID stay fixed. |
| Stale or unexpected public deployment | Accept the canonical **production** deployment only on exact commit SHA and verified project identity. Also fetch the canonical Pages hostname without credentials or redirects and compare its HTML byte for byte with the approval. |
| Credential or customer-data exposure | Keep OAuth grants and job state separate. Use fixed application diagnostic codes. Treat private HTML, site copy and contact emails as customer data. Worker invocation logs and traces are a separate operator-controlled data surface. |

These controls assume the Worker code, dedicated D1, encryption key and provider APIs are trusted. A GitHub owner can independently move the production branch or change Pages settings. This may cause Pages to build a different revision between the last branch check and the actual build. The review discloses Git-connected deployments and the service only records the approved revision as verified. Avoid out-of-band changes during the acceptance run.

## State and recovery

| State | Transition |
| --- | --- |
| Private preview | Explicit approval creates a queued job in D1. Preview alone carries no launch authority. |
| Queued | Claim a two-minute lease. Reconcile or create the exact private repo and starter files, then record the commit containing the approved homepage before requesting Pages creation. Record the verified Pages project ID and transition to deployment verification. |
| Pending deployment | Claim a lease and check only the recorded project, production branch, commit and HTML. Leave the job pending when Pages or the public response has yet to converge. |
| Needs reauthorization | Pause when the session or either provider grant becomes invalid. Resume after a new approval by the same verified owner and account, after any old lease has expired. |
| Failed | Stop after a permanent conflict or retry exhaustion. An eligible owner can review and approve the same snapshot again once the cause is resolved. A recorded identity and SHA stay pinned. |
| Live | Show the site and verified revision. The launch runner performs no further work on this job. |

Each phase has five attempts. Retryable timeouts, network errors, provider throttling, transient server failures and selected create conflicts use 30, 60, 120 and 240 second delays, with a bounded provider `Retry-After` of up to 600 seconds. The HTTP check buttons use the same due time and lease as Cron. The runner counts attempts when it claims work, so repeated interruption also consumes the retry budget. The owner can see attempts and next eligibility along with a safe result code. Jobs with no active approval and expired history are reconciled in bounded batches.

Delivery is at least once. Creating the repository, homepage and Pages project is individually reconciled by their verified identities and exact configuration. A job-specific repository marker supports recovery before the first checkpoint. The GitHub Contents create omits a blob SHA, so a competing existing file cannot be overwritten. The approved revision is stored before Pages creation and stays fixed if the provider accepts the request but loses its response. The provider names and subsequent reads make retries converge without relying on a cross-provider transaction.

Migration 0004 retains legacy approved receipts, including approvals whose receipt write was interrupted. Legacy rows carry no automatic authority. After explicit reapproval, a legacy marked repository is eligible for reuse only if private, owned by the same GitHub user, limited to the starter tree and already contains the exact approved HTML. A legacy partial repo without that file requires owner attention. The runner preserves unrelated or conflicting customer resources.

## Retention and rollout

- Keep durable history for 30 days from the first approval, including when the original session ends. The authorized owner can delete completed or inactive history before expiry. Cleanup removes the job, short-lived binding, and associated private previews. Customer-owned GitHub and Pages resources remain under customer control. Cloudflare D1 Time Travel has its own backup window. Include this and the preview, consent and deletion policies in the customer privacy notice. [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)
- Before deployment, coordinate with the backend owner and the domain/OAuth agent. Confirm the dedicated `launch-and-own-onboarding-beta` D1 name, ID and account. In the authorized operator environment, run `wrangler d1 migrations list DB --remote --config onboarding/wrangler.jsonc` from the repository root. Proceed only when `0004_launch_jobs.sql` is the sole pending migration. Pause legacy provisioning entry points and Cron for the controlled transition.
- Apply the pending migration with `wrangler d1 migrations apply DB --remote --config onboarding/wrangler.jsonc` after owner approval. Wrangler records 0004 in the ledger alongside 0001–0003. Run the read-only `node onboarding/validate-config.mjs --remote` with the operator's approved credentials and require `schema-ready` with four ordered migrations, the durable tables and columns, and the preview cleanup trigger. [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/)
- Deploy through the owner-approved process after the remote preflight and CI pass. Require `/health` to report `configured` and `launchJobsReady`. Check runtime logs for fixed-code `runner_unavailable` events and review invocation-log and trace capture. Restrict or redact OAuth callback query strings, authorization headers and cookies before exposing the service. Coordinate any configuration updates through the domain/OAuth handoff. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
- During controlled beta acceptance, verify real consent, Cloudflare's separate Pages GitHub App access, interruption and resume, one repository/project pair, logout and grant revocation, and the exact production result. Track failed and paused jobs via their safe result codes without adding site text or credentials to alerts.
- For rollback, pause HTTP launch actions and scheduled delivery, let admitted calls settle, and keep the additive 0004 schema and checkpoints. Prefer a fix forward using those checkpoints. Older Worker versions lack these fences. Keep launch entry points and Cron stopped if an older version must be restored, invalidate affected sessions under operator control, and ask customers to reconnect and reapprove after restoring a compatible runner. If restoring D1 from a backup, invalidate restored sessions and confirm job checkpoints against actual provider effects before restarting delivery.

`npm test` covers the SQL migration, approval races, duplicate scheduled delivery, provider failures after resource creation, session expiry, logout mid-request, revoked access, account isolation, retry exhaustion and exact deployment verification. The test suite uses simulated providers and a local database. Live provider consent, rollout and public-beta acceptance are separate operator gates.
