# Post-launch Web Analytics: read-only foundation (#85)

**Status (2026-11-22): implemented in code on an unmerged feature branch; not deployed or customer-accepted.** This slice is *not* Analytics enablement, a visit counter, customer-facing UI, or a claim that a site is collecting data. It exists to give the #87 dashboard a conservative server-side adapter after #39 owner inventory is complete.

## Cloudflare evidence and limitations

- [Cloudflare Pages: Enable Web Analytics](https://developers.cloudflare.com/pages/how-to/web-analytics/) documents **Workers & Pages > select project > Metrics > Enable**. Enabling this may add a client-side JavaScript performance/traffic beacon **on the next deployment**. Do not silently consent, trigger builds, or change existing static site files.
- [Cloudflare Pages project GET API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/methods/get/) supports `GET /accounts/{account_id}/pages/projects/{project_name}` with Pages Read (or Pages Write) permission. The documented project model provides `build_config.web_analytics_tag` and `build_config.web_analytics_token`. The adapter reads **only the documented tag field** as unverified configuration evidence and never returns the tag, token, arbitrary provider JSON, environment variables, or user data.
- [Web Analytics limits](https://developers.cloudflare.com/web-analytics/limits/) lists **10 tracked sites not proxied via Cloudflare** versus no limit for proxied sites, and plan-dependent rules (Free: 0 custom rules). Do not assume these quota rules apply identically to every Pages site/account configuration. #84 owns per-customer plan/scopes/entitlement truth.
- Metrics dashboards and API querying are **not implemented** here. A project tag does **not** prove the beacon is present in the deployed HTML, that data has arrived, that Core Web Vitals are available, or that visitor counts are zero. Respect privacy disclosures and relevant consent requirements before enabling real-user monitoring.

## Read-only owner-account audit (2026-11-22, GPT-6)

Using the existing **connected owner account** and Cloudflare GET APIs only, I listed Pages projects and Web Analytics registration records, then independently fetched each of the three visible `esp-*` managed Pages projects by its project name. **All three individual project GETs succeeded**, had GitHub source and `main` production branch, and **0/3 reported `build_config.web_analytics_tag` or `web_analytics_token`**. The account-level RUM site list was readable and included **four registered Web Analytics sites**, none with a tag matching these three managed Pages projects. No secrets, project IDs, site tags or private account records were copied into this repository.

**Interpretation:** This verifies *no Pages analytics configuration tag observed on those three managed projects at audit time*. It does **not** prove a lack of external analytics scripts, rule out other accounts or sites, verify visitors/traffic, establish a plan limit, or prove those sites have no beacon through some other mechanism. Do not surface an `active_verified` state based on this result. No Cloudflare resource or site content was changed during the audit. Account Settings Read supports Web Analytics registration GET; Pages Read supports Pages project GET. More general per-user scopes and paid/free truth remain assigned to #84.

## Adapter contract

`pipeline/pages-analytics.mjs` exports `readPagesAnalyticsStatus({site, principal, cloudflareAccessToken, assertCurrentAuthorization, fetchFn?})`.

Both `site` and `principal` **must be supplied by the trusted backend**, never from a browser query, form, agent message, or client-controlled JSON. `site` is the immutable current managed-site inventory from #39 (verified GitHub user ID, repo ID, account ID, Pages project ID, project name, GitHub owner/repo, `main`); `principal` is the authenticated and freshly authorized session's GitHub user ID and selected Cloudflare account ID. **The required `assertCurrentAuthorization(frozenSiteIdentity)` callback must independently re-read current backend session/grant validity, authorization epoch, selected Cloudflare account, and this site's stable GitHub/Cloudflare identities, returning `true` only if all still match.** The adapter invokes it before GET, after the HTTP response and after the JSON await. Missing/failed fencing yields `blocked_permission_or_plan`, with no provider call or dashboard links. The caller must refresh OAuth access tokens server-side and keep the currently authorized repository identity current. The adapter snapshots trusted IDs before awaiting network work, then refuses results if caller-supplied identity objects changed during I/O. **It does not revalidate GitHub's live user identity by itself; that remains the #39 caller's responsibility.**

After the identity gate, the only network request is `GET` to the account-specific Pages project. The exact Pages project ID, `pages.dev` subdomain, GitHub repo name/ID/login, optional provider-reported GitHub `owner_id`, canonical numeric repo ID, production branch, source type and static output rules must match the trusted site record. The adapter passes `ownerId` to the updated shared #95 matcher and performs the owner-ID and canonical-repository checks locally until #95 is integrated. Any mismatch fails closed without returning dashboard links.

The returned feature projection contains `feature`, `state`, `reason`, `configuration`, `metrics`, `action`, `projectDashboardUrl` and `analyticsDashboardUrl` only. It never exports secrets, raw provider response fields, a customer site URL, or user metrics. UI consumers should show **manual setup** and open the verified project in the owner's Cloudflare dashboard only after a successful project match. The Cloudflare dashboard may still require the user to sign in and select the correct account. **Only the verified project dashboard link is emitted**: `analyticsDashboardUrl` is intentionally `null` because an account-scoped global Web Analytics deep link is not documented reliably. From the verified project, use **Metrics > Web Analytics**. Never send a placeholder `:account` link or promise that a global dashboard path is stable.

| State / configuration | UI meaning |
| --- | --- |
| `manual_setup` + `not_observed` | Verified project is readable; enablement *not established*. Open its Cloudflare Metrics UI to inspect or opt in manually. |
| `manual_setup` + `tag_reported_activation_unverified` | Project GET reports a Web Analytics tag; activation, beacon injection, live data and visits are **not independently verified**. |
| `blocked_permission_or_plan` | Missing/expired session fence, missing/revoked token (**401 → reauthentication required**) or non-throttled **403 → permission denied**. Distinct safe reason codes, no links. |
| `not_available` | HTTP 404 means the named Pages project was inaccessible, **not** that Web Analytics is unsupported. Rate limiting, server errors, redirects, provider transport failures and invalid provider JSON produce sanitized temporary/unexpected-response reason codes and no links. |
| Ownership mismatch exception | Unmatched Pages project or GitHub source fails closed. The caller must never leak an internal exception message in UI. A network error or provider exception containing tokens is instead converted into a sanitized unavailable status without links. |

All five metric data fields, including visitors, pageviews and Core Web Vitals, remain `null` and `metrics.status='not_queried'`. No `active_verified` is possible from this phase. No quotas/plan entitlements are invented.
