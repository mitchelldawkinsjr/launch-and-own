# Optional post-launch execution — Agent 2 / #88

## Status and release boundary

The post-launch **domain** and **email** execution path is implemented for a separately authorized, exact D1 grant, but **disabled by default**. The contact-form resource path is **not available** until #89 separately approves the usage/cost, privacy, retention, customer-owned D1 and server-side Turnstile Siteverify plan, and independent customer acceptance succeeds. A displayed Turnstile widget or a stored forms review never means a working form exists.

This code ships the execution mechanism, not permission to run production mutations. Do **not** deploy or apply migrations, expand OAuth scopes, enable flags, or create live operator grants until Domain #2 and Sol #83 sign off. #21 independent customer test is not run by this work. #53 onboarding redesign is unchanged.

## Two independent, immutable records

1. `onboarding_option_approvals` from `0005_option_approvals.sql` stores the existing site's customer-reviewed domain/email/forms request. Its only status is `stored`. The existing `/site-options` flow recomputes the digest. Email's shared `buildEmailRoutingApprovalReview` hashes the **exact mailbox, alias, hostname, GitHub user and Cloudflare account**. No Cloudflare/GitHub request happens on approval.
2. `onboarding_option_executions` from additive `0006_option_executions.sql` is a **different**, operator-authorized D1 row. There is no public creation endpoint. An authorized Domain/operator reviewer must independently inspect the customer's real current job, exact `0005` row, Cloudflare account, repository ID, Pages project ID, main SHA, session epoch, scope and consent, then create an out-of-band approved execution grant with that exact immutable snapshot. A browser or stored review does **not** authorize a provider write.

The operator grant contains `id` (UUID), `option_approval_id` (the current actual stored row ID), `job_id`, GitHub numeric user ID, Cloudflare account ID, `kind`, canonical `approval_digest`, **normalized** `payload_json` (domain `{"hostname":"www.example.com"}`; email `{"hostname":"www.example.com","mailbox":"verified@external.example"}`), immutable `repository_id`, `pages_project_id`, `expected_commit_sha`, `authorization_epoch`, unique `operator_grant_id`, bounded `approved_at/expires_at`, `status='approved'`, `updated_at`. The normalized payload must exactly match `validateStoredOptionApproval`, not arbitrary client JSON. Site and consent remain bound to the separately stored row. Replacing a consent row, changing account/repo/Pages/SHA, reauthorizing a session or expiring the grant invalidates it.

The only execution endpoint is same-origin, CSRF-protected `POST /site-options-execute` with exactly `csrf` and an opaque execution `id`. It appears as an **Apply operator-approved ...** button on the existing options screen **only after** all D1 grants and site/tenant checks pass. This is not a second consent screen. No public route creates a grant. All controls are OFF unless `OPTION_EXECUTION_ENABLED='true'` and the exact per-kind `OPTION_DOMAIN_ENABLED='true'` or `OPTION_EMAIL_ENABLED='true'` are operator-set environment flags. These flags are intentionally absent from the checked-in Wrangler configuration; **do not enable by default**.

The D1 adapter `onboarding/option-execution-store.mjs` rechecks the selected owner session, account, current live job, stored review digest/payload, Pages project ID, repo ID and SHA before execution. `approved → applying` uses one atomic owner/account/job/kind/digest/full-payload/project/SHA/epoch/expiry/session-fenced SQL CAS plus unique lease token. Exactly one claimant can win. Provider POST authorization checks the same applying D1 lease and only the exact hostname or literal `contact@` forwarding rule. `applying → applied` requires a matching lease and records a receipt. Failure leaves `needs_reconciliation` (no blind automatic retry or replay); an operator must verify provider state and separately decide cleanup/reapproval.

The application verifies the live private GitHub repo ID, owner, production branch and **current main SHA**, and the exact Git-integrated Cloudflare Pages project, before claiming. OAuth tokens are decrypted/refreshed only on the backend from the current session. The provider adapter follows no redirects, does no automatic retry, and has bounded GETs.

## Domain: exact Cloudflare Pages hostname only

After customer review + trusted operator grant + current-session validation, `pipeline/cloudflare-extension-provider.mjs` may POST **only** `/accounts/{owner account}/pages/projects/{matching project}/domains` with the canonical reviewed hostname. It then reads back the Pages domain. `attached_pending_dns` means the attachment exists but **DNS/TLS may not be ready**; this is not the same as a verified active website. It never writes DNS, MX, NS, SPF, DKIM, buys a domain, changes paid plans, or migrates hosting.

## Email: a separate dependent grant, no MX

The email execution grant must be separate from domain. `pipeline/approved-extension-consumer.mjs` requires an **applied execution row** for the **same job/user/account/hostname** and the currently active exact Pages domain. It independently requires an active **same-account Cloudflare zone**, **already-ready Email Routing/DNS**, a complete read-only proof that the **exact receiving hostname** has Cloudflare's three routing MX targets (`route1` / `route2` / `route3.mx.cloudflare.net`), a preexisting **verified external forwarding destination**, and no conflicting alias/rule. Cloudflare Email Routing at the apex **does not automatically enable forwarding on subdomains**: the owner must independently enable that particular subdomain in Cloudflare's Email Routing settings. This can add DNS records, so it is manual, out of band, never an automatic action from these reviews. If DNS Read scope is missing, the path fails closed. It may create **only** one exact `contact@hostname` literal-recipient forward rule with the reviewed destination. It does **not** create an inbox, send outgoing mail, send address verification email or update MX. Cloudflare zone and Email Routing permissions are not in the current Pages-only OAuth grant; explicit provider-approved additional scopes must be obtained later. The provider reads routing rules from the account-level Cloudflare endpoint and requires each matching rule to carry the exact previously verified zone tag. After creating a rule, it performs a second exact-alias readback with the expected rule ID, owner zone, matcher and forwarding mailbox before saving an applied receipt. `routing_rule_recorded` is **not** a delivery or inbound email acceptance guarantee; a consenting owner must send a test email and confirm receipt separately. Cloudflare's actual Email Routing list responses may omit `total_pages`; a complete first page is therefore validated against `total_count` (and any available `total_pages`), never accepted when truncated. A read-only owner-account audit showed that using the zone ID in the `/accounts/{id}/email/routing/rules` path can fail with HTTP 403 even though the account-level list works.

## Contact form staging

An approved forms execution can stage a managed Turnstile widget and its dedicated customer D1 with a current, separately approved #89 cost/privacy grant and an operator grant. The receipt binds each stage to its reviewed resource, and the result keeps `workingForm` false while exact Worker deployment and owner acceptance are pending. Static hosting works independently of the form. [Forms staging](CUSTOMER_FORM_WORKER.md) · [Cost and privacy approval](FORMS_COST_PRIVACY_APPROVAL.md)

## QA / operational checklist

- `npm test` includes tenant, changed digest, wrong repo/Pages/SHA, expired/replaced consent, session epoch, negative forms, email-before-applied-domain, single-winner CAS, exactly one domain POST, and no unauthorized MX/Cloudflare/GitHub writes.
- `npm run qa:distribution`, `npm run preflight:onboarding`, and Worker recovery rehearsal must pass before merge.
- The read-only remote preflight requires the complete **0001–0010 ledger and physical schema** in the dedicated onboarding beta D1. Use the repository's Wrangler migration runner for approved schema changes. Domain coordinates migrations and leaves `OPTION_FORMS_ENABLED` unset outside an approved pilot.
- Rollback of code does not remove a domain, email rule or submitted personal data. Any provider unlink/cleanup requires a separately reviewed tenant-specific action. An uncertain write stays in reconciliation state until an owner confirms the real resource.
